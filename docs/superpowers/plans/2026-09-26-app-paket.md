# App-Paket Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** MTG-Player als ZIP zum Entpacken für Windows, das sich per Doppelklick startet und sich selbst aktualisiert.

**Architecture:** Die Bridge bekommt einen App-Modus (`-Dmtgplayer.app=true`): freie Ports, Browserfenster, Fassungsauskunft, Update-Prüfung und -Anwendung. Der Paketbau dünnt Forges `res` auf den benutzten Teil aus, stellt einen Ordner zusammen und lässt `jpackage` Starter samt Java-Laufzeit erzeugen; ein GitHub-Workflow macht daraus bei jedem Versions-Tag ein Release mit ZIP und Prüfsumme.

**Tech Stack:** Java 17 (`jpackage`, `java.net.http`), Maven, React/Vite, GitHub Actions (`windows-latest`), Windows-Batch für den Ordnertausch.

**Spec:** `docs/superpowers/specs/2026-09-26-app-paket-design.md` – bei Widersprüchen gilt die Spec.

### Task 1: App-Modus – Ports, Fenster, Schreibprüfung

**Files:**
- Create: `bridge/src/main/java/mtgplayer/app/AppMode.java`
- Modify: `bridge/src/main/java/mtgplayer/Main.java`
- Create: `bridge/src/test/java/mtgplayer/app/AppModeTest.java`

**Interfaces:**
- Produces: `AppMode.enabled()` (liest `mtgplayer.app`), `AppMode.freePort(int wunsch)`, `AppMode.openWindow(String url)`, `AppMode.writableOrNull(Path appDir)`.

- [ ] **Step 1: Die fehlschlagenden Tests schreiben**

`AppModeTest`:
- `freePort` liefert den Wunschport, wenn er frei ist (Port ab 18100 wählen, nie 8080/8081).
- Ist der Wunschport belegt (im Test selbst mit einem `ServerSocket` belegen), liefert `freePort` einen anderen, **freien** Port – und nicht denselben.
- `writableOrNull` liefert `null` für ein beschreibbares Verzeichnis (`@TempDir`) und einen erklärenden Text für ein nicht beschreibbares (Verzeichnis ohne Schreibrecht anlegen; ist das auf dem Testsystem nicht möglich, den Test überspringen statt ihn weichzuklopfen – und das im Bericht sagen).
- `openWindow` wird **nicht** getestet, indem ein Browser startet: die Kommandozeilen-Bildung wird als reine Funktion geprüft (`AppMode.windowCommand(browserPfad, url)`), der Start selbst bleibt ungetestet.

- [ ] **Step 2: Tests laufen lassen – sie müssen scheitern**

```bash
cd <worktree>/bridge && timeout 590 mvn -q -Dtest=AppModeTest -DfailIfNoSpecifiedTests=false test
```

- [ ] **Step 3: `AppMode` schreiben**

- `enabled()`: `Boolean.getBoolean("mtgplayer.app")`.
- `freePort(int wunsch)`: `wunsch` testweise binden; klappt es, `wunsch` zurückgeben, sonst mit `new ServerSocket(0)` einen freien holen. Zwischen Prüfen und Benutzen liegt immer ein Rennen – der Kommentar sagt das, und der Aufrufer behandelt einen Bindefehler als Fehler mit klarer Meldung statt als Absturz.
- `windowCommand(Path browser, String url)`: `[browser, "--app=" + url]`.
- `openWindow(String url)`: der Reihe nach `msedge.exe`, `chrome.exe` an den üblichen Windows-Pfaden (`%ProgramFiles%`, `%ProgramFiles(x86)%`, `%LOCALAPPDATA%`), sonst `Desktop.browse`. Jeder Fehlschlag führt zum nächsten Schritt, der letzte Fehlschlag wird gemeldet, nicht geworfen – ohne Fenster läuft die App weiter und nennt die Adresse im Text.
- `writableOrNull(Path appDir)`: Probe-Datei anlegen und löschen; klappt das nicht, Text „Bitte den Ordner an eine Stelle entpacken, an der du schreiben darfst (nicht C:\\Programme)."

- [ ] **Step 4: In `Main` einhängen**

Im App-Modus: Ports über `AppMode.freePort(...)`, `mtgplayer.web` als Vorgabe auf `app/web` **relativ zum App-Ordner** (der App-Ordner kommt aus `mtgplayer.assets`), nach dem Start des HTTP-Servers `AppMode.openWindow(...)` mit der tatsächlichen Adresse, und die Schreibprüfung **vor** `ForgeBoot.init()`, damit die Meldung kommt, bevor Forge startet. Ohne `mtgplayer.app` bleibt alles wie heute – das ist der Weg, den Kevins Entwicklungs-Bridge nimmt.

- [ ] **Step 5: Tests laufen lassen, committen, Cherry-Pick**

```bash
cd <worktree>/bridge && timeout 590 mvn -q -Dtest=AppModeTest -DfailIfNoSpecifiedTests=false test
grep -h "Tests run" target/surefire-reports/*.txt
cd <worktree> && git add bridge/src && git commit -m "bridge: app-modus mit freien ports, eigenem fenster und schreibpruefung

Co-Authored-By: Claude Opus 5 <noreply@anthropic.com>"
cd /home/kevin/projects/MTG-Player && git cherry-pick $(git -C <worktree> rev-parse HEAD)
```

### Task 3: Paketordner zusammenstellen

**Files:**
- Create: `scripts/package.sh`

**Interfaces:**
- Consumes: `scripts/trim-res.sh`.
- Produces: `scripts/package.sh <version> <ziel>` erzeugt den vollständigen Paketordner und ruft `jpackage`.

- [ ] **Step 1: Skript schreiben**

Reihenfolge: Bridge-Jar und Abhängigkeiten sammeln (`mvn -q dependency:copy-dependencies -DoutputDirectory=…` plus das eigene Jar), `web/dist` nach `app/web` kopieren, `trim-res.sh` nach `assets/res`, `LICENSE` und `forge/MODIFICATIONS.md` (als `MODIFICATIONS.txt`) hineinlegen, `version.txt` schreiben, dann

```
jpackage --type app-image --name MTG-Player --input <app> --main-jar bridge-<v>.jar \
  --main-class mtgplayer.Main --app-version <version> \
  --java-options "-Xmx4g" --java-options "-Dmtgplayer.app=true" \
  --java-options "-Dmtgplayer.assets=\$APPDIR/../assets" --java-options "-Dmtgplayer.web=\$APPDIR/web"
```

`$APPDIR` löst jpackage zur Laufzeit auf; die genaue Schreibweise gehört geprüft, nicht geraten – ein Lauf mit `--verbose` und ein Blick in die erzeugte Konfiguration zeigen, was ankommt. Das Skript läuft auf Linux (dort entsteht ein Linux-App-Image) und auf Windows unverändert über Git-Bash im Workflow; plattformabhängig ist nur der Name der erzeugten Startdatei.

- [ ] **Step 2: Lokal ausprobieren**

Paket lokal bauen, das erzeugte App-Image starten (Ports ab 18100 setzen, damit Kevins Bridge unberührt bleibt), im Browser die Lobby öffnen, eine KI-Partie starten. Was dabei auffällt, kommt in den Bericht; Screenshot ist hier nicht nötig, ein laufendes Spiel schon.

**Files:**
- Create: `bridge/src/main/java/mtgplayer/app/UpdateApply.java`

**Interfaces:**
- Produces: `UpdateApply.run(Release r, Path appDir, Consumer<String> zustand)`; Nachrichten `applyUpdate` und `updateState`.

- [ ] **Step 1: Die fehlschlagenden Tests schreiben**

Mit eingesetzter Download-Quelle und `@TempDir`:
- Erfolgsfall: ZIP mit bekanntem Inhalt und passender Prüfsumme → entpackt in den Zwischenordner, `update.cmd` liegt daneben und enthält die beiden Ordnernamen; der App-Ordner ist **unverändert**.
- Falsche Prüfsumme → Abbruch mit Fehlerzustand, kein Zwischenordner bleibt liegen, App-Ordner unverändert.
- Quelle wirft → derselbe Abbruch.
- Zustandsfolge: `laden`, `pruefen`, `entpacken`, `neustart` in dieser Reihenfolge; im Fehlerfall endet sie mit `fehler`.

- [ ] **Step 2: Tests laufen lassen – sie müssen scheitern**

- [ ] **Step 3: Umsetzen**

Herunterladen nach `%TEMP%`, SHA-256 rechnen und vergleichen, entpacken (Pfade im ZIP prüfen: kein Eintrag darf aus dem Zielordner herausführen – ein ZIP aus dem Netz wird nie blind entpackt), `update.cmd` schreiben: auf das Ende des Prozesses warten, alten Ordner nach `<Name>.old` umbenennen, neuen an seine Stelle schieben, App starten, bei Erfolg `.old` löschen, bei Fehlschlag zurückbenennen. Das Skript läuft aus `%TEMP%`, nicht aus dem App-Ordner – sonst tauscht es den Ordner aus, in dem es selbst liegt.
